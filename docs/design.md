# Kinora design

Kinora records what a Minecraft client receives, rebuilds the world from it without a server, lets
the user film it again with a keyframed camera, and renders the result offline, frame by frame, at
exact simulated times.

This document is the architecture. The file format is in [format.md](format.md), the Minecraft and
NeoForge facts it relies on are in [internals.md](internals.md), and every mixin is justified in
[mixins.md](mixins.md).

## 1. Modules

| Module | Depends on | Holds |
| --- | --- | --- |
| `kinora-core` | Java, Gson, aircompressor (zstd) | `.kinora` container, recording writer and ring buffer, camera and timeline math, project model, render clock, image writers, FFmpeg pipe, audio mixer |
| `kinora-api` | nothing | the public surface for other mods (`dev.kinora.api`) |
| `kinora-mc` | core, api, Minecraft, NeoForge | capture, playback, camera control, offline renderer, UI |
| `kinora-inspector` | core | `kinora-inspect` command-line tool |
| `sample-mod` | api | a mod that records and replays its own effect |

`kinora-core` has no Minecraft imports and is tested with plain JUnit. Everything that would have to
change when Minecraft changes lives in `kinora-mc`, and inside it the version-fragile parts sit behind
small adapter classes in `dev.kinora.mc.adapter` (see [UPGRADING.md](../UPGRADING.md)).

## 2. Recording

### 2.1 What is captured

1. **Clientbound frames.** A Netty handler (`CaptureHandler`) is inserted into every client
   `Connection` pipeline directly in front of the packet decoder, by one mixin at the tail of
   `Connection.configurePacketHandler`. It sees every frame as bytes (VarInt id + body) after
   decryption and decompression, in multiplayer and singleplayer alike (the integrated server
   serializes too). It copies frames whose inbound protocol is CONFIGURATION or PLAY into PACKET
   records. Capturing bytes rather than decoded objects is lossless: bundle delimiters, split
   payloads and payloads of mods the recorder does not know all survive.
2. **Decoded packets for the state model.** A second handler in front of `packet_handler` sees the
   decoded `Packet` objects in the same order and feeds the snapshot model (2.3). A FIFO of ordinals
   pairs each decoded packet with the frames it came from (one frame, or a whole bundle).
3. **The recording player.** The server never sends a player its own movement, head yaw, equipment,
   swing or the sounds and level events it causes. At the end of every client tick Kinora writes a
   CLIENT_STATE record: position, rotations, pose flags, equipment changes, swings, vehicle position,
   camera FOV and perspective.
4. **Sounds.** A `SoundEventListener` sees every sound the client starts, with the resolved file,
   volume, pitch, position, attenuation distance and category. SOUND records keep them with sub-tick
   timing. Those caused locally (not by a sound packet) are replayed from these records; packet
   sounds are regenerated by playback, with the same seed and therefore the same variant.
5. **Markers** from the marker hotkey and from event detection.
6. **Mod data** written through the API.

### 2.2 Timing

Every record carries the number of completed client ticks at the moment it was produced and the
monotonic nanoseconds since the recording started. During playback, records with tick `t` are
applied right after playback tick `t` completes, which is the moment the live client would have
processed them. Rendering between ticks `t` and `t+1` uses the partial tick, exactly as the live
client did.

### 2.3 Snapshots

A SNAP chunk lets playback start at a later point without replaying everything before it. It is
built from a packet-level model of client state, updated as packets are decoded:

* configuration phase, login and the last respawn: kept;
* per chunk: the last chunk-data packet plus later block, light and block-entity updates; dropped on
  forget;
* per entity: its spawn packet, merged entity data, equipment, attributes, passengers, effects, and an
  absolute position tracked through the relative move packets (`VecDeltaCodec`), written as a
  synthesized `ClientboundEntityPositionSyncPacket`; dropped on removal;
* latest value of: time, weather, chunk cache center and radius, world border, spawn, abilities,
  tab list, boss bars, scoreboard, map data, player info;
* packets the model does not understand (including other mods' payloads): kept, capped per type;
* mod data tracks contribute their own state through the API.

Most entries are references to earlier records by ordinal, so a snapshot is small. A snapshot is
written every 30 seconds of recording (configurable) and at dimension changes.

The same model makes the **instant replay buffer** possible: the buffer keeps records in memory for
a window of N minutes plus whatever the newest snapshots reference; committing writes a new file that
starts with a snapshot materialized into plain records. **Clip export** uses the same machinery on a
finished file.

### 2.4 Writer

`RecordingWriter` (core) owns the file on a background thread. Producers append records through a
synchronized method that assigns the ordinal, so ordinal order is append order across threads. A
byte-bounded queue absorbs bursts; if the disk cannot keep up and the queue exceeds its budget the
recording stops cleanly with a warning instead of stalling the network thread or silently dropping
data. Records are batched into PKTS chunks of about 256 KiB or one second, compressed with zstd.
The file is synced every 5 seconds. A crash loses at most the unsynced tail.

### 2.5 Lifecycle

One connection is one file. Server transfer or disconnect ends it; reconfiguration and dimension
changes stay in the same file (they are just packets). Modes: manual start/stop, auto-record on join
(per server/singleplayer), instant replay buffer, marker hotkey. A free-space check stops recording
with a warning before the disk fills.

## 3. Playback

### 3.1 The session

Playback builds an ordinary client connection with no server behind it:

* a Netty `EmbeddedChannel` with Minecraft's own pipeline (`configureSerialization`,
  `configurePacketHandler`) and a real `Connection`;
* a `ClientConfigurationPacketListenerImpl` with a `CommonListenerCookie` whose profile is a fresh
  camera identity (random UUID) and whose `ServerData` is a synthetic entry marked as a Kinora replay;
* recorded frames are written into the channel **on the game thread**, so every handler runs inline
  and protocol switches complete synchronously.

Outbound packets are discarded. Because nothing about the player's real worlds, servers or options
is involved, playback cannot alter them. Leaving playback disconnects this connection the normal way
(`Minecraft.disconnectFromWorld`), which also reverts NeoForge's registry snapshot.

### 3.2 The playback filter

A handler in front of `packet_handler` rewrites decoded packets before the listener sees them:

* login and respawn: the camera gets a reserved entity id and SPECTATOR mode; the recorded player id
  is free for the puppet;
* packets that act on the local player (position, health, inventory, screens, abilities, game mode,
  death, resource packs, transfer, code of conduct, dialogs) are dropped;
* player chat is rewritten as system chat, so seeking never trips the chat index check.

### 3.3 The puppet

The recording player is a `RemotePlayer` with the recorded id and UUID, spawned after login and every
respawn, and driven from CLIENT_STATE records at the end of each tick (position, rotations, equipment,
swing). Its `PlayerInfo` comes from the recorded tab list.

### 3.4 Time

`ReplayClock` owns replay time as an integer tick plus a fraction. One mixin into `Minecraft.runTick`
replaces the number of ticks the timer returns with the number the replay clock wants, and lifts the
10-ticks-per-frame cap during fast-forward; another overrides `DeltaTracker.Timer`'s partial tick. Speed
(0.01x to 10x), pause, frame step and loops are all clock operations. Animated textures tick once per
replay tick.

### 3.5 Seeking

Forward within a short distance: run ticks without rendering. Otherwise: tear the session down, start
a new one, apply the latest snapshot at or before the target, then fast-forward. A loading overlay
shows progress for long seeks.

### 3.6 Camera

The camera is not an entity. Each frame `CameraDirector` computes a `CameraState` (double position,
yaw, pitch, roll, FOV) from the active mode (free, follow, orbit, spectate, locked, or the timeline),
and a mixin into `Camera.update` applies it after `alignWithEntity`. FOV goes through
`Camera.calculateFov`. The camera LocalPlayer is moved to the camera position every tick so player-
centred effects (ambient particles, sounds) happen where the camera is.

### 3.7 Overrides

Time of day, weather, entity visibility, HUD, chat, nametags, particles and skins are render-time
overrides applied by the playback filter or by render events. They never feed back into the stream.

## 4. Cinematography

All camera math is in core, in double precision.

* `CameraState`: position, yaw, pitch, roll, FOV (with lens conversion), shutter angle.
* Tracks hold keyframes with per-segment interpolation: hold, linear, Catmull-Rom (uniform and
  centripetal), Bezier with handles, eased variants (sine, quad, cubic, expo, custom cubic-bezier).
* Paths can be re-parameterized by arc length for constant speed; rotations interpolate as quaternions
  (slerp/squad) with shortest-path or forced direction.
* Constraints and rigs: look-at with smoothing and blend weight, follow and orbit with damping.
* Time remap maps output time to replay time (speed ramps, freeze, reverse) with sub-tick accuracy.
* Shake is seeded noise: deterministic for a given seed and time.
* A project holds shots; a sequence arranges shots with cuts and transitions.

## 5. Rendering

* `RenderClock` steps output frames by exact rational time: frame `i` is at `i * den / num` seconds,
  so `duration * fps` frames are produced and no frame is ever dropped or doubled.
* For each frame the renderer computes replay time through the time remap, drives the replay clock to
  that tick and partial tick, waits until the world has settled (no queued section compiles, no
  expected chunks, stable section count, skins loaded), renders, and reads back asynchronously.
* Motion blur renders N sub-frames spread evenly across the shutter interval and accumulates them in a
  float target. Tiled rendering offsets the projection matrix per tile. Resolution above the window
  uses the window-size override vanilla uses for panoramas.
* Frames stream to FFmpeg through a pipe, or to PNG/EXR sequences. Audio is mixed offline from the
  sound records and the sounds playback produces, resampled through the time remap.
* Deterministic by construction except where documented: GPU driver differences, particle randomness
  unless re-seeded, other mods using wall-clock time.

## 6. Threads

| Thread | Touches |
| --- | --- |
| Netty event loop (recording) | `CaptureHandler`, state model (under the recorder lock) |
| Game thread | playback channel, packet handling, camera, rendering, UI, CLIENT_STATE and SOUND records |
| Kinora writer | the open `.kinora` file |
| Kinora loader | reading and decompressing chunks for seeking and the browser |
| Kinora encoder | the FFmpeg pipe and image writers |

No rendering call happens off the game thread; no file IO happens on it.

## 7. Risks

| Risk | Mitigation |
| --- | --- |
| A Minecraft update renames handlers or packets | all touch points listed in internals.md; adapters; UPGRADING.md checklist |
| NeoForge disconnects a replayed configuration (mod mismatch) | compatibility check before loading; clear message naming the missing mods |
| Snapshot model misses some state | snapshots validated in tests against full replays; unknown packets kept; fallback to replay from start |
| Chat index check disconnects after a seek | player chat rewritten as system chat |
| Entity id or UUID collision between camera and puppet | reserved camera id, random camera UUID |
| Wall-clock visuals break determinism | redirected during renders (glint, border, chunk fade); documented remainder |
| Readback stalls | asynchronous ring of mapped buffers |
| VRAM exhaustion at 8K | checks against `maxTextureSize`, tiling, clear message |
| Shader mods replace the pipeline | detect, warn, degrade (no motion blur or passes) rather than crash |
| Recording slows the game | capture copies bytes only; everything else on the writer thread; overhead measured |
